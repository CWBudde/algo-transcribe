# NEON GEMM kernels for `nn`: Go tiles versus NEON, and js/wasm

Date: 2026-10-11 (PLAN 4.1).

## Setup

| Item  | Value                                                       |
| ----- | ----------------------------------------------------------- |
| CPU   | Apple M5 Pro (15 cores as seen by Go)                       |
| OS    | macOS 27.0.1 (build 26A434)                                 |
| Go    | go1.27.1 darwin/arm64                                       |
| Node  | v24.12.0 (js/wasm runs)                                     |
| Input | random data (`nn`), fixture `vocal` window 0 (`basicpitch`) |

## Method

- **Go tiles versus NEON, native.** The same commit is built twice as test
  binaries, once with `-tags purego` (the Go tiles, exactly the code js/wasm
  runs) and once without (NEON). The two binaries run alternately, one
  `-test.count 1` run each per round, for 10 rounds:
  - `nn`: `BenchmarkConv2DWindow` (one basic-pitch convolution over a full
    172-row window, im2col included) and `BenchmarkGemm` (one `gemm` call of
    the layer's shape, m = 8, without im2col).
  - `basicpitch`: `BenchmarkModelForward` (the whole CNN for one window).
- **js/wasm.** Test binaries of `main` (d0c86ee) and of this branch, both
  `GOOS=js GOARCH=wasm`, run alternately in Node through `go_js_wasm_exec`
  (`env -i` to avoid Node's environment limit), 5 rounds.
- The default benchtime of 1 s applies.

**Machine load.** Other sessions were running on the machine (load average
3 to 20 during the native runs, 7 to 14 during the wasm runs), and Go places
benchmark goroutines on performance and efficiency cores alike, so single
runs spread by up to ±40 %. The tables therefore give the **minimum** over the
runs, which is the uncontended performance-core figure, next to the median.
The minimum is the better estimate here: the Go-tile window minimum, 38.8 ms,
matches the 38.6 ms median PLAN 2.2 measured for the same code on an idle
machine (`2026-10-10-model.md`). Because the variants alternate, load affects
both sides of every comparison alike.

The multi-channel kernel reaches 60 to 64 GMAC/s at k = 200 and 936, about
four times the Go tiles' 16 GMAC/s. The GEMM of the single-channel layers is
four times faster as well, but their window gains only 1.5 to 1.8 ×: im2col
copies as many values as these layers multiply (PLAN 1.1), and it now
dominates them. conv2d_2 (k = 49) pays for its short k loop: the horizontal
reductions and the k%4 tail are a larger share of 12 k steps.

## Layout choice: dot form versus outer product

Both layouts PLAN 4.1 names were implemented as complete prototypes and
measured against each other, interleaved, 20 runs each
(`BenchmarkConv2DWindow`, multi-channel layers; same load caveat, minimum and
median):

| Layer    | Go tiles min | Dot form min | Outer product min | Dot median | Outer median |
| -------- | -----------: | -----------: | ----------------: | ---------: | -----------: |
| conv2d_1 |     23.58 ms |  **7.59 ms** |           7.96 ms |    9.19 ms |      9.76 ms |
| conv2d_2 |      1.91 ms |      0.87 ms |       **0.76 ms** |    1.14 ms |      0.96 ms |
| conv2d_4 |      6.59 ms |      2.08 ms |       **2.03 ms** |    2.78 ms |      2.69 ms |
| sum      |     32.08 ms | **10.54 ms** |          10.75 ms |            |              |

- **Dot form** (chosen): 4 × 4 tiles over the transposed weights
  `wt[co*k+i]`, accumulators vectorised over k, FADDP reduction at the end;
  8 × 1 tiles with 16 accumulators for n = 1.
- **Outer product**: 8 × 8 tiles over the HWIO k × n weights, by-element
  `FMLA` (WORD-encoded), accumulators hold the outputs directly.

The two are within 2 % over the multi-channel layers. The outer product wins
conv2d_2, whose short k makes the dot form's reductions visible, and the dot
form wins conv2d_1, which is 62 % of the Go-tile window and still 49 % of
the NEON one. The dot form was kept
because it also covers n = 1 with the same layout, needs no second weight
copy in `Conv2D` and no change to `conv.go`, and keeps `gemmSIMD`'s operands
identical to those of the Go tiles, which 4.2 can reuse.

No difference is significant (geomean of the layers +0.12 %). Under js/wasm
`gemmSIMD` is the stub, which the compiler inlines into `gemm` and on into
`Conv2D.row` as a constant false (checked with `-gcflags=-m`), so the code
that runs is the Go tiles as before. The absolute wasm times are about 9 %
above PLAN 2.2's idle-machine 96.3 ms because of the load.

## Commands

```bash
# native: Go tiles vs NEON, alternating test binaries
go test -c -o nn-neon.test ./nn/ && go test -c -tags purego -o nn-go.test ./nn/
go test -c -o bp-neon.test ./basicpitch/ && go test -c -tags purego -o bp-go.test ./basicpitch/
for r in $(seq 10); do for v in go neon; do
  (cd nn && ../nn-$v.test -test.run '^$' -test.bench 'Conv2DWindow|Gemm' -test.benchmem -test.count 1 >> ../nn-$v.txt)
  (cd basicpitch && ../bp-$v.test -test.run '^$' -test.bench ModelForward -test.benchmem -test.count 1 >> ../bp-$v.txt)
done; done

# js/wasm: main vs branch, alternating, in Node
GOOS=js GOARCH=wasm go test -c -o nn-branch.wasm ./nn/   # likewise for main and basicpitch
env -i PATH="$PATH" HOME="$HOME" "$(go env GOROOT)/lib/wasm/go_js_wasm_exec" \
  nn-branch.wasm -test.run '^$' -test.bench Conv2DWindow -test.benchmem -test.count 1
```
