# basic-pitch CNN: full window and ForwardJob steps

Date: 2026-10-10 (PLAN 2.2).

## Setup

| Item    | Value                                        |
| ------- | -------------------------------------------- |
| CPU     | Apple M5 Pro (15 cores as seen by Go)        |
| OS      | macOS 27.0.1 (build 26A434)                  |
| Go      | go1.27.1 darwin/arm64                        |
| Node    | v24.12.0 (js/wasm runs)                      |
| Input   | harmonic stack of fixture `vocal`, window 0  |
| Weights | embedded `basicpitch/weights.bin` (PLAN 1.2) |

## Method

Benchmarks are in `basicpitch/model_bench_test.go`:

- `BenchmarkModelForward` runs `Model.Forward` on one window (172 frames). The
  realtime factor is the new audio per window, 36164 / 22050 s = 1.640 s,
  divided by the time per window.
- `BenchmarkForwardJobStep/<stage>` advances a `ForwardJob` to the stage, so
  every input of the stage is a real activation. It then repeats single steps
  of that stage by rewinding the job's row cursor. Only full row blocks are
  timed. A step includes the activation, and for `conv2d_4` also the concat
  into the 33-channel tensor.
- `BenchmarkForwardJobMaxStep` runs full passes of 395 steps, timing each step
  with `time.Now`. It reports the longest wall time of any step over all passes
  of a run (`max-step-ns`) and the mean step. This is wall time, so it includes
  scheduler and GC jitter.

Commands, run from the repository root:

```bash
# native, 10 runs
go test ./basicpitch/ -run '^$' -bench 'Model|ForwardJob' -benchmem -count 10

# js/wasm in Node, 5 runs (env -i avoids Node's "environment exceeds limit")
env -i PATH="$PATH" HOME="$HOME" GOOS=js GOARCH=wasm \
  go test -exec="$(go env GOROOT)/lib/wasm/go_js_wasm_exec" \
  ./basicpitch/ -run '^$' -bench 'Model|ForwardJob' -benchmem -count 5
```

All numbers are medians over the runs. The default benchtime of 1 s applies.

## Single step per stage

The number of rows per step is `max(1, 2^20 / MACsPerRow)`. Stage time is
derived as step cost × 172 / rows; it is not measured separately.

| Stage            | Rows/step | Steps | Native step | wasm step | Native stage | wasm stage |
| ---------------- | --------: | ----: | ----------: | --------: | -----------: | ---------: |
| conv2d_1         |         1 |   172 |    139.2 µs |  349.2 µs |      23.9 ms |    60.1 ms |
| contours-reduced |        19 |    10 |    254.2 µs |  557.2 µs |       2.3 ms |     5.0 ms |
| conv2d_2         |         7 |    25 |     88.0 µs |  274.4 µs |       2.2 ms |     6.7 ms |
| conv2d_3         |        17 |    11 |    196.8 µs |  362.0 µs |       2.0 ms |     3.7 ms |
| conv2d_4         |         1 |   172 |     43.7 µs |  109.3 µs |       7.5 ms |    18.8 ms |
| conv2d_5         |        40 |     5 |    211.6 µs |  426.6 µs |       0.9 ms |     1.8 ms |
| **sum**          |           |   395 |             |           |      38.8 ms |    96.1 ms |

All step benchmarks report 0 B/op and 0 allocs/op.

The derived stage times add up to the measured window (38.8 vs 38.6 ms
native, 96.1 vs 96.3 ms wasm). PLAN 1.1 measured the six convolutions alone
(random data) at 37.0 ms native and 95.5 ms wasm. So the activations and the
concat add about 0.8 to 1.6 ms per window. This is approximate, because the
runs and inputs differ.

## Largest single step

| Target  | Largest step (isolated)    | Wall-time max over full passes, median of runs | Worst run |
| ------- | -------------------------- | ---------------------------------------------: | --------: |
| native  | contours-reduced, 254.2 µs |                                         402 µs |   6.41 ms |
| js/wasm | contours-reduced, 557.2 µs |                                         704 µs |   5.26 ms |

A throwaway per-step diagnostic run (50 passes, native) confirmed this
ranking. Steps 172 to 180, the full blocks of contours-reduced, have the
highest median, about 0.25 ms. The wall-time maximum, however, falls on
random conv2d_1 steps whose median is 0.14 ms. So it measures jitter, not a
more expensive step. The multi-millisecond worst runs (native 4.22 and
6.41 ms, wasm 5.26 ms) coincide with runs whose time per pass was also high
(native 41.0 and 51.6 ms against a 38.6 ms median). The machine was not idle
during the runs.

### Re-run on an idle machine

After the other work had finished, `BenchmarkForwardJobMaxStep` was run again
with `-count 5`, natively and under js/wasm, with nothing else running:

| Target  | `max-step-ns` per run (µs) | Median | Mean step | Time per pass |
| ------- | -------------------------- | -----: | --------: | ------------: |
| native  | 275, 282, 368, 425, 702    | 368 µs |   97.8 µs |       38.6 ms |
| js/wasm | 572, 947, 952, 1133, 1231  | 952 µs |  240.9 µs |       95.2 ms |

Natively, no step took more than 0.71 ms of wall time on the idle machine.
Under js/wasm in Node, the slowest step of a run varies from 0.57 to 1.23 ms,
although no step costs more than 0.56 ms in isolation. The spread comes from
the runtime (Go's wasm scheduler and GC, and Node), not from the step size.

## Interpretation

- **Native target (≤1 ms per step): met.** The largest step costs 0.25 ms
  (contours-reduced, 19 rows). The typical wall-time maximum over a whole pass
  is 0.40 ms.
- **js/wasm in a 2 ms budget:** the largest step costs 0.56 ms, 28 % of the
  budget. The wall-time maximum over a pass is 0.70 ms (median during the
  busy runs) to 0.95 ms (median on the idle machine), at most 1.23 ms, so a
  caller should check the clock between steps rather than plan a fixed number
  of steps per slice. A mean step of
  0.245 ms allows about 8 steps per 2 ms slice. A full window of 395 steps
  then takes about 50 slices.
- **The step budget is uneven.** `modelStepMACs` sizes blocks by MACs, but the
  single-channel layers run at roughly a third of the GEMM throughput (PLAN
  1.1). So their steps (contours-reduced, conv2d_5, conv2d_3) cost 1.4 to 1.8
  times a conv2d_1 row natively, while a conv2d_4 row costs a third of one.
- **conv2d_1 dominates the window:** about 62 % of the native and the wasm
  time, followed by conv2d_4 at about 19 %.
